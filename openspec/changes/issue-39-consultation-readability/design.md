# Readable consultation without changing music

In performance mode, show a compact one-octave theoretical keyboard and spelled chord tones directly on each chord in the song sketch. All diagrams remain visible without first selecting each chord; selection still synchronizes the exact performed parts. A short label explains that chord tones are theoretical and that the arrangement below shows what is played. Retain the larger selected reference in edit mode, bounded by its sketch row.

The shared PerformedPiano keeps its 80px white-key geometry when editable. In consultation, keyboards are horizontal rows with bounded key widths and proportional height. Every visible performed pitch has its own readable key label and non-color marker; the complete note list and out-of-view warning remain. Narrow screens use bounded horizontal scrolling instead of distorting keys. Independent range controls remain available under an explicit disclosure. Part names, hands, sounds and per-part ownership remain visible, including silence and overlapping layers. View changes remain local and never transpose or mutate music.

Verify multiple independently correct chord diagrams before selecting them, real hit-testing, key proportions, visible selected-pitch labels, bounded narrow scrolling, two/three-octave views, 200% text, edit target size, unchanged library content and axe checks. Existing editor/offline/private journeys remain required. Screenshots use only synthetic songs; a physical tablet and musician remain separate acceptance.

Current deployment instructions must distinguish anonymous IndexedDB and private PostgreSQL acknowledgements. Release preparation stays bound to committed source; origin, OIDC and operator secret files must be supplied privately before any actual Internet deployment.

Bind both the refused request and cookie query to the already safety-checked selected application origin, assert the response origin and actual HTTPS Secure cookie, and rerun all 44 cases without an unrelated Development service.
