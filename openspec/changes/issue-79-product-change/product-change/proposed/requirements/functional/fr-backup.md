## Requirement

The product MUST provide a documented, versioned portable ScoreMap data envelope with explicit scope, field meaning, schema version, source-revision provenance, compatibility and migration rules. Export MUST preserve every field in its declared authorized scope: stable song, section, measure and event identities/order/positions/durations/repeats; spelled harmonic identity; exact performed pitches and octaves; independent arrangements/parts/voicings; optional hands; device/range/layer/sound bindings; repertoires/memberships; reminders/references; and supported attachments with complete required bytes and associations. Explicitly included owned preferences, presets and reusable configuration in contexts allowing their transfer MUST retain ownership distinction and copied version provenance. Export MUST NOT change source music or imply pending work is acknowledged. Credentials, usable sessions/provider material and authority-conferring grants MUST NOT be exported.

Existing anonymous browser import MUST remain explicitly confirmed complete replacement after whole-envelope validation. Valid empty replacement MUST remain possible. Cancellation, malformed data, duplicate identities/memberships, dangling associations, invalid pitch/timing/values, incomplete attachments, unsupported versions and unsupported capabilities MUST leave the previous durable library unchanged. Explain refusal rather than silently drop unsupported fields or merge unselected songs. Unsupported browser/service attachment transfer MUST remain refused until that independent capability is supported.

Supported browser v1 migration MUST preserve existing song/repertoire/section/membership/reminder/reference identities, order, repeats and triad spelling. New measure/event identities, timing defaults and the unassigned default arrangement MUST follow BR-STRUCTURE; theoretical keyboard references MUST NOT be fabricated into performed notes. A durable migration receipt MUST preserve generated identity mappings across retries. Migration MUST retain a recovery copy, validate complete content and activate atomically at its declared boundary. Unknown versions and failed migration MUST preserve source and previous acknowledgement without replacement.

Anonymous-to-account claim and private-service import MUST require real authentication, current online resource capability, explicit selection, preview and confirmation. Derive destination ownership from trusted session identity, not imported owner/grant values. Identity collision MUST refuse before mutation and offer explicit copy-as-new with a previewed, consistently remapped set of associations; no silent overwrite or merge. Principal-bound receipts MUST make retry/reconciliation idempotent. Original anonymous work MUST remain until verified authorized service reconstruction, and source removal MUST require explicit user choice. Session cleanup MUST NOT erase it. An origin change MUST require explicit export from the old origin, not a claim that another origin can read retained local work.

Each acknowledged private-service import boundary MUST contain a complete valid song and owned content. Independently owned preferences and reusable resources MUST have separate explicit acknowledgements; song grants MUST NOT transfer access to the owner's other resources. Multi-song service work MUST declare commit boundaries and receipts, making partial progress recoverable and visible. No result may claim one atomic transaction across independent device and service stores. Complete reconstruction MUST preserve all new musical fields, not only a triad sketch.

Private-service export/history/restoration MUST enforce current capability and BR-SESSION, including fresh online reconnect checks. Protected retained work MUST NOT permit export after authority expires or is revoked. Deleted private-song export/history requires the current owner's fresh online permission; former grants confer none. Backup restoration MUST reconcile deleted/purged identities and current authorization. Purged identities MUST NOT resurrect through retries or stale restore. Distinguish portable musician transfer from operator disaster recovery and never promise instant erasure of old exports/backups.

Native Android MUST export/share one complete selected current acknowledged song or complete ordered set with all required songs, supported musical dependencies and song-owned content. Preserve known key, lyrics and chord associations, cues, phrase data, exact pitches/order/timing/hands/parts and musical binding information. Copy required reusable musical definitions into the portable graph. Supported owned PDFs MUST travel with their bytes and integrity reference, not broken source-device paths; external links MUST remain explicit links without an offline remote-content promise. Include format/capability version and source revision/provenance, but not private local revision history, app preferences, actual hardware configuration, runtime hardware authority or account/session/grant authority. Imported content MUST start independent destination history. Complete PDF transfer is required native acceptance, not a waived future capability.

Native import MUST validate and preview the entire graph and its consistent identity mapping before confirmation, always create independent editable local copies, and preserve all existing destination music/resources. It MUST NOT perform replacement, overwrite, merge or same-identity update, even on collision. Remap every local identity and reference consistently while preserving shared dependencies and ordered membership. A deliberately new import MAY create another copy; the same command's retry/reconciliation MUST reuse its result and mapping.

The whole selected native song/set graph, required copied definitions, initial destination histories, identity mapping and command receipt MUST have one atomic local activation boundary with qualified required-attachment publication before acknowledgement. Invalid/unknown/truncated/oversized/unsupported/incomplete content, duplicates, dangling references, cancellation, storage exhaustion and attachment failure MUST preserve original files and prior durable music without partial activation, silent omission or false success. An ambiguous response MUST reconcile actual receipts. The independent source installation and external document/share route are not part of the destination transaction.

Verification MUST independently compare complete source and reconstructed values at actual declared boundaries. Native local round trips MUST NOT count as authenticated second-session recovery. For native acceptance, use two independent installations with existing unrelated destination music, transfer a complete synthetic song and ordered set through available document routes, then edit, re-export and reopen the imported result. Record unavailable messaging/email routes honestly. Existing private journeys MUST use the same file-driven manual/automated real-login contract, execution-scoped reset and actual service reconstruction; no bypass is introduced. Real operator inputs, credentials and private libraries remain outside public evidence; Production rejects development identity/configuration defaults.

## Rationale

Portability preserves complete music without imported authority, destination loss or confusion among independent native exchange, browser replacement and private-service recovery.
